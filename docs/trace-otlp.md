# Выгрузка трасс по OTLP

```lua
otlp.start({ endpoint = 'http://otel-collector:4318', service_name = 'panel' })   --> true
otlp.flush()   -- дослать накопленное, не дожидаясь такта: перед остановкой узла
otlp.stop()    -- цикл встал, запись отрезков выключена
```

`tnt-trace-otlp` доставляет закрытые отрезки
[`tnt-trace`](https://github.com/tnt-skein/tnt-trace) в коллектор
OpenTelemetry по OTLP/HTTP в JSON, сжатом gzip: фоновый файбер забирает
партии из очереди трассы, шлёт их коллектору и разбирает его ответы
по правилам OTLP. При старте он же собирает свой клиент `tnt-http`,
ставит крюки трассы — клиентских отрезков и отрезков сообщений
загруженным очередям — и включает запись в `tnt-trace`: приложение
получает трассы в Tempo, Jaeger или Grafana без единой своей строки
сверх `otlp.start`.

Зависимости: [`tnt-trace`](https://github.com/tnt-skein/tnt-trace)
(очередь закрытых отрезков, крюки клиента HTTP и очередей),
[`tnt-http`](https://github.com/tnt-skein/tnt-http) (клиент
к коллектору), [`tnt-retry`](https://github.com/tnt-skein/tnt-retry)
(правило `Retry-After`), [`tnt-loop`](https://github.com/tnt-skein/tnt-loop)
(фоновый цикл), [`tnt-compress`](https://github.com/tnt-skein/tnt-compress)
(gzip), [`tnt-log`](https://github.com/tnt-skein/tnt-log) (журнал
и правило тайн), [`tnt-clock`](https://github.com/tnt-skein/tnt-clock)
(монотонные часы повтора), [`tnt-must`](https://github.com/tnt-skein/tnt-must)
(проверки аргументов) и
[`tnt-external`](https://github.com/tnt-skein/tnt-external) (подмена
часов, имени узла, признака Sentry и загруженных очередей в проверках).

## Зачем пакет

`tnt-trace` закрытые записанные отрезки только складывает в очередь
с потолком — вывезти их с узла приходится отдельной работой. Её и делает
выгрузчик:

- **Говорит с коллектором на его языке.** Три правила ProtoJSON коллектор
  проверяет строго — опознаватели шестнадцатеричной строкой, время
  десятичной строкой, род и статус целыми, — и ошибка в любом из них
  стоит всей партии (раздел «Что уходит коллектору»). Ответы коллектора
  разбираются по OTLP: что повторить, что выбросить, сколько ждать.
- **Узел его не ждёт.** Отрезок кладётся в очередь без уступки
  управления, партия уходит из фонового файбера, а набравшаяся полная
  партия будит цикл, не дожидаясь такта (раздел «Партии и такт»).
- **Клиентские отрезки и отрезки сообщений — без своей строки.**
  `start` ставит крюк `tnt-http`, и каждая попытка исходящего обращения
  становится отрезком `client` в трассе. Загруженным очередям
  [`tnt-queue`](https://github.com/tnt-skein/tnt-queue),
  [`tnt-event`](https://github.com/tnt-skein/tnt-event),
  [`tnt-amqp`](https://github.com/tnt-skein/tnt-amqp),
  [`tnt-kafka`](https://github.com/tnt-skein/tnt-kafka) он ставит крюк
  сообщений: отправка — отрезок `producer`, обработка — `consumer` под
  ним, и трасса не рвётся на границе очереди.

**Почему отдельный пакет, а не часть `tnt-trace`.** Выгрузчику нужны
`tnt-http` и `tnt-loop`, а `tnt-trace` берут все, кому нужен лишь
`trace_id` в журнале: тянуть за трассой клиент HTTP с его повторами
и проверкой настроек значило бы ставить его каждому. Пакет, законно
зависящий и от трассы, и от клиента, — естественное место, где крюки
трассы ставятся сами: `start` зовёт
`trace.install(trace.present(http, lookup))`, и клиентские отрезки
исходящих обращений и отрезки сообщений появляются в трассе вместе
с выгрузкой. Очереди договора выгрузчик спрашивает по имени и только
загруженные (`package.loaded`): зависимости от них у него нет,
а незагруженной очереди крюк ставить некуда. Очередь, загруженная после
старта, крюк получает следующим стартом — ядро приложения зовёт его
на каждом применении настроек — либо `trace.install` самого приложения;
до того её видно по `trace.status().hooks`.

**JSON, а не protobuf.** Коллектор принимает оба тем же путём, а бинарный
protobuf на чистом Lua — отдельный кодировщик на сотни строк со своими
проверками. JSON собирает встроенный `json` Tarantool, а размер тела
держит сжатие (раздел «Сжатие»).

## Как пользоваться

```lua
local trace = require('tnt.trace')
local otlp = require('tnt.trace.otlp')

trace.configure({ sample_rate = 1 })                  -- настройки трассы — до старта выгрузки

otlp.start({
    endpoint = 'http://otel-collector:4318',          -- к адресу дописывается /v1/traces
    service_name = 'panel',                           -- ресурс service.name
    resource = { ['deployment.environment'] = 'stand' },
    headers = { authorization = 'Bearer …' },         -- коллектору с ключом
})                                                    --> true

trace.within('report.build', function() end)          -- записанный отрезок ждёт в очереди

otlp.flush()       --> { { spans = 1, ok = true, status = 200, rejected = 0 } }
otlp.status()      --> { running = true, recording = true, sending = false, spans = { accepted = 1, … }, … }
otlp.stop()        -- цикл остановлен, запись выключена, крюки и будильник остаются
```

| Вызов | Что делает |
|---|---|
| `start(opts)` | собирает клиент к коллектору, ставит крюки `trace.install` клиенту `tnt-http` и загруженным очередям договора, включает `trace.record(true)`, ставит будильник очереди `trace.on_filled(batch, …)`, запускает цикл; отдаёт `true` либо `nil, err`, если очередь отрезков снимает Sentry (раздел «Очередь снимает кто-то один») или клиент не собрался (негодный адрес, ключ без сертификата, заголовок, который ставит выгрузчик, gzip на узле без zlib) — идущая выгрузка при этом остаётся как была; негодная форма настроек — исключение на строке вызывающего. Повторный вызов перенастраивает: прежний цикл гасится, клиент собирается заново, ждущая партия и очередь остаются |
| `stop()` | останавливает цикл и выключает запись; крюки и будильник остаются — остановленный цикл толчок не будит; накопленное не шлёт — остановка не ждёт коллектора; до старта ничего не делает |
| `flush()` | отправляет всё, что накопилось: ждущую партию, если её срок пришёл, и партии из очереди — полные подряд, неполную последней; идущую отправку ждёт до конца; отдаёт список исходов, пока выгрузка не запущена — `nil, err` |
| `status()` | `{ running, recording, sending, endpoint, service_name, batch, interval, retries, compression, spans, batches, pending, last_error }` |
| `encode`, `reply` | части — кодировщик JSON и приговор ответу — для тех, кто собирает своё |

Исход отправленной партии в списке `flush()`:

| Исход | Вид |
|---|---|
| принята | `{ spans, ok = true, status, rejected }` |
| отложена на повтор | `{ spans, ok = false, status, retry_in, err }`; без ответа `status` пуст |
| выброшена | `{ spans, ok = false, status, err, cause }`; `cause` — `refused` (коллектор отказал так, что повтор не поможет), `exhausted` (повторы кончились) либо `too_long` (сервер просит ждать дольше потолка) |

Настройки `start`:

| Настройка | Что значит | Умолчание |
|---|---|---|
| `endpoint` | адрес коллектора, `http` или `https`; к нему дописывается `/v1/traces`, путь самого адреса остаётся приставкой: `http://gw/otlp` — `http://gw/otlp/v1/traces` | `http://127.0.0.1:4318` |
| `service_name` | имя службы в ресурсе (`service.name`) | обязательна |
| `resource` | атрибуты ресурса сверх имени службы: имена — непустые строки, значения — строки, числа, `boolean`; `service.instance.id` здесь главнее имени узла, `service.name` — отказ | — |
| `headers` | заголовки на каждое обращение к коллектору | — |
| `client` | прочие настройки `tnt-http`: `ca_file`, `ssl_cert`, `ssl_key`, `unix_socket`, `connect_timeout`, `user_agent`, `layers`; шесть настроек задаёт сам выгрузчик (раздел «Клиент выгрузчика») | — |
| `batch` | отрезков в партии | 512 |
| `interval` | период такта, секунды | 1 |
| `timeout` | срок обращения к коллектору, секунды; складывается со сроком соединения клиента (3 с) | 5 |
| `retries` | повторов партии сверх первой попытки | 5 |
| `compression` | сжатие тела партии: `gzip` (`Content-Encoding: gzip`) либо `none` — как есть (раздел «Сжатие») | `gzip` |

Ресурс партии: `service.name` из настройки, `service.instance.id` — имя
инстанса из `box.cfg`, если узел настроен, и `resource` сверх того.
Область инструментирования — `tnt-trace`.

Порядок важен: `trace.configure` — до `otlp.start`. `configure` берёт
настройки трассы целиком, и не названный в нём `record` выключает
запись, которую включил `start`. Это видно в `status()`: `running = true`
при `recording = false` — цикл идёт, а выгружать ему нечего.

## Клиент выгрузчика

Собирается явно при старте. Шесть его настроек задаёт сам выгрузчик,
и в `client` их не передают — такая попытка бросает исключение, а не
пропадает молча:

- **`base_url`, `headers`, `timeout`** — приходят настройками старта
  `endpoint`, `headers`, `timeout`;
- **`propagate = false`** — отправка партии, случись она в чьей-то
  области, иначе завела бы клиентский отрезок о самой себе, и тот попал
  бы в следующую партию; заголовки контекста коллектору тоже незачем;
- **`retry = { attempts = 1 }`** — повторы ведёт выгрузчик, иначе два
  цикла перемножились бы;
- **`max_redirects = 0`** — коллектор никуда не переезжает; ответ
  переходом — отказ, партия выбрасывается.

```lua
otlp.start({ service_name = 'panel', client = { retry = { attempts = 3 } } })
-- error: настройки выгрузки трасс.client.retry задаёт выгрузчик: повторы партии ведёт выгрузчик
```

Партия уходит `POST /v1/traces` с `Content-Type: application/json`
и, пока сжатие не выключено, `Content-Encoding: gzip`. Эти два заголовка
ставит выгрузчик, и в `headers` их не передают: заголовок запроса
главнее заголовка клиента, и названный там пропал бы молча. Такая
попытка — отказ `start` парой, а не исключение, как и прочие негодные
заголовки: их проверяет сборка клиента, и тот, кто сверил форму
настроек заранее, получает отказ значением, а не броском посреди
применения.

```lua
otlp.start({ service_name = 'panel', headers = { ['Content-Encoding'] = 'identity' } })
--> nil, клиент к коллектору не собран: заголовок Content-Encoding задаёт выгрузчик: сжатие — настройкой compression
```

Срок ответа — `timeout` (5 с); у `tnt-http` он складывается со сроком
соединения (3 с по умолчанию, меняется через `client.connect_timeout`).
Схема адреса сверяется при старте: клиент к `ftp://` собрался бы
и отказывал только на отправке, и узел молча повторял бы партию до конца
повторов. Учётные данные из адреса в отказе, в `status().endpoint`
и в записи о старте вырезаны.

## Очередь снимает кто-то один

Очередь `tnt-trace` одна на узел, и отрезки из неё забирает кто-то
один: либо этот выгрузчик, либо приёмник Sentry с отрезками — модуль
`tnt.sentry`. Двое забирали бы друг у друга партии, и каждая трасса
приходила бы в оба приёмника с дырами. Поэтому второй из них
не запускается, кто бы ни пришёл первым: Sentry с отрезками отказывает
при идущем выгрузчике, а `start` выгрузчика — пока Sentry снимает
очередь:

```lua
-- загружен tnt.sentry, и его status().takes_spans = true
otlp.start({ service_name = 'panel' })
--> nil, 'очередь отрезков tnt-trace уже снимает tnt-sentry: остановите его
--       либо перезапустите Sentry без отрезков (spans = false)'

-- Sentry перезапущен без отрезков: status().takes_spans = false
otlp.start({ service_name = 'panel' })                --> true
```

Отказ — парой, как у клиента, который не собрался: занятая очередь —
состояние узла, а не ошибка в настройках, и идущая выгрузка при нём
остаётся как была. Тот, кто зовёт `start` на каждом применении своих
настроек, получает этот текст значением и остаётся с прежней выгрузкой.

Выгрузчик спрашивает у загруженного модуля `tnt.sentry` его признак
`status().takes_spans` — истинный, пока Sentry снимает очередь.
Зависимости от Sentry у пакета нет: незагруженный модуль очереди
не снимает. Запись трассы (`recording`) признаком служить не может:
её включает и сам выгрузчик, и тот, кто настраивает трассу,
и перенастройка рядом с Sentry без отрезков видела бы в ней соседа,
которого нет.

## Партии и такт

Узел выгрузки не ждёт никогда: отрезок кладётся в очередь `tnt-trace`
без уступки управления, а сверх потолка (2048) новый отбрасывается
и считается (`trace.status().dropped`). Партия уходит из фонового
файбера `trace_otlp` на `tnt-loop`: такт — раз в секунду либо как только
в очереди набралась партия (512 отрезков). Цикл берёт партии подряд:
полная уходит следующей сразу, неполная — последняя в такте. Первый такт
идёт сразу при старте и отправляет то, что накопилось до него.

**Полная партия будит цикл.** `start` ставит будильник очереди
`trace.on_filled(batch, …)` (документ
[`tnt-trace`](https://github.com/tnt-skein/tnt-trace/blob/main/docs/trace.md),
«Будильник очереди: `on_filled`»):
отрезок, которым в очереди набралась партия, толкает цикл (`loop:wake()`),
и такт идёт, не дожидаясь конца периода. Толчок не уступает управления —
файбер, закрывший отрезок, выгрузки не ждёт, — а такт начинается, как
только тот уступит сам. Толчок посреди такта не теряется: следующий такт
идёт за ним без паузы. Так узел, рождающий больше `capacity / interval`
отрезков в секунду, их не теряет, пока коллектор успевает: 5000 отрезков
за 0,1 с при такте в час уходят без единого отброшенного. Звонок один
на переход через порог: пока партия ждёт повтора, растущая очередь
цикл не дёргает. `stop()` будильник не снимает — остановленный цикл
толчок не будит, — а следующий `start` ставит его с новым `batch`.

**Отправка одна за раз.** Такт цикла и ручной `flush()` ждут друг
друга: вместе они поделили бы ждущую партию — отправили бы её дважды,
а их неудачи затёрли бы одна другую, и партия пропала бы без счёта.
Пока отправка идёт, `status().sending = true`. Остановка и перенастройка
посреди отправки дают дойти партии, которая уже в пути, но следующей
та отправка не берёт: клиент уже не тот. `flush()`, ждавший её и
переживший остановку, отдаёт `nil, 'выгрузка трасс не запущена'`.

## Ответы коллектора

Приговор выносит `tnt.trace.otlp.reply` по правилам OTLP/HTTP:

| Ответ | Что делается |
|---|---|
| 2xx | партия принята; `partialSuccess.rejectedSpans` — только целое больше нуля и не больше партии — считается отвергнутым (`spans.rejected`), и пишется `warn` с причиной коллектора; такие отрезки не повторяются: коллектор отверг их осознанно |
| 429, 502, 503, 504 | повтор той же партии с отступом по степени двойки: 1, 2, 4, 8, 16, 30 с; пока партия ждёт, новые отрезки копятся в очереди до потолка, а новых партий цикл не берёт |
| нет ответа: сеть, срок | как 503; причина — без адреса коллектора |
| 400 и всё прочее | партия выбрасывается и считается (`spans.discarded`, `batches.discarded`, `cause = 'refused'`): 400 значит, что партия негодна, и OTLP запрещает её повторять; 500, 401, 302 не лечат ни время, ни повтор |

`Retry-After` читает тот же судья, что у `tnt.retry` и `tnt-http`, —
только число секунд: дата меряется чужими часами. Названный срок —
нижняя граница: повтор не раньше него и не раньше отступа по степени
двойки. Просьба ждать дольше потолка (30 с) выбрасывает партию
(`cause = 'too_long'`): прийти раньше значит сделать то, о чём просили
не делать, а ждать дольше — держать очередь без выгрузки по чужому слову.

Повторов у партии не больше `retries` (5) сверх первой попытки; после —
партия выбрасывается с записью `warn` (`cause = 'exhausted'`). Миг
повтора отмечается настоящими монотонными часами и сверяется на такте:
повтор уходит первым тактом после срока, то есть с опозданием
до `interval`.

Счётчики в `status()`: `spans` — `accepted`, `rejected`, `discarded`;
`batches` — `sent`, `retried`, `discarded`; `pending` — ждущая партия
(`spans`, `attempt`, `retry_at` — миг монотонных часов); `last_error` —
чем кончилась последняя неудача. Заголовки в `status()` не показываются.

Журнал — `tnt.trace.otlp`, с подавлением повторов подряд: `info` о старте
(`endpoint`, `service_name`, `batch`, `compression`) и остановке; `warn`
об отложенной партии (`spans`, `attempt`, `status`, `err`), о выброшенной
(то же и `cause`), об отвергнутых отрезках (`rejected`, `err`)
и о сорвавшемся такте (`err`).

## Повтор после потерянного ответа

Коллектор мог принять партию, а ответ до узла не дошёл: оборвалось
соединение, истёк срок, прокси на пути ответил 502 или 504. Выгрузчик
не отличает такую партию от непринятой и шлёт её снова — ту же до байта,
с теми же `span_id`. Узел видит это как повтор (`batches.retried`,
`warn` «партия отрезков не принята, повтор»), а в `spans.accepted`
отрезок считается один раз: что первая копия дошла, узел не знает.
Сколько раз отрезок покажут, решает хранилище трасс. Tempo проверен
на стенде (`make otel-up`: Tempo 2.10.3, Grafana 12.4.2):

| Когда копия дошла до Tempo | Что видно |
|---|---|
| пока трасса живая: с её последнего отрезка прошло меньше `ingester.trace_idle_period` (у Tempo 2.10 по умолчанию 5 с, в стенде 1 с) | отрезок **дважды**, как только Tempo закроет трассу, — в трассе (`/api/traces/<trace_id>`) и в поиске TraceQL (`{ name = "…" }` находит два); уплотнение блоков копий не сводит. Пока трасса живая, её выдача показывает копии одной строкой, а поиск её ещё не находит |
| трасса уже закрыта | отрезок один раз: Tempo сводит копии из разных записей трассы при чтении, а уплотнение — и в хранилище |
| в обоих случаях | метрики, которые Tempo считает по отрезкам (`traces_spanmetrics_calls_total`), считают и копию: вызовов на один больше |

Tempo сводит копии с одним `span_id`, только если они лежат в разных
записях трассы. Повтор, пришедший, пока трасса живая, ложится в ту же
запись. Окно отсчитывается от последнего отрезка трассы, пришедшего
в Tempo с любого узла. Повтор после обрыва соединения при такте
по умолчанию уходит через 1–2 с после первой копии и при умолчаниях
Tempo попадает в окно. Повтор
после истёкшего срока (`timeout`, 5 с) уходит позже, и трасса, в которую
больше ничего не приходило, к нему может быть уже закрыта. Поэтому дубль
не редкость, но и не правило, и отличать его приходится по виду.

**Как это выглядит у оператора.** Grafana рисует в трассе две строки
с одним именем, началом и длительностью, и счётчик `N spans` над
отрезками на один больше. Вторую копию Grafana помечает опознавателем
`<span_id>_1`. Панели по метрикам отрезков завышают число вызовов.

**Как отличить повтор от настоящего отрезка.** Копия совпадает
с оригиналом во всём: `span_id`, имя, миги начала и конца, род,
родитель, атрибуты. Настоящий отрезок, даже с тем же именем и в тот же
миг, получает свой случайный `span_id`. Два отрезка с одним `span_id`
в одной трассе — повтор партии, и считать их надо один раз.

**Как найти отрезок поиском.** Tempo 2.10 по `{ span:id = "…" }`
не находит отрезок, чей `span_id` начинается с нулевого байта (`00…`), —
это каждый 256-й из случайных опознавателей. Выдача трассы
по `trace_id` и поиск по имени отрезка его находят, и `spanID`
в выдаче поиска записан полностью, с нулями. Поэтому копии на стенде
считаются поиском по имени отрезка со сверкой `span_id` в выдаче.

## Сжатие

Тело партии по умолчанию сжимается gzip и уходит с
`Content-Encoding: gzip`: OTLP это разрешает, а коллектор разжимает тело
по заголовку. Настройка `compression` — `gzip` либо `none`; имена —
те, что OpenTelemetry даёт переменной `OTEL_EXPORTER_OTLP_COMPRESSION`,
чтобы одно слово значило одно и то же на всём пути отрезка. Умолчание —
`gzip`: полная партия — больше двухсот килобайт JSON в секунду, и сеть
узла и коллектора одна на всех. `none` — для коллектора или прокси,
который gzip не читает.

Сжимает [`tnt-compress`](https://github.com/tnt-skein/tnt-compress) на третьем уровне,
`otlp.GZIP_LEVEL`. Сжатие — счёт в потоке событий узла, как
и кодирование JSON. Замер на 3.8 — партия в 512 серверных отрезков
со случайными опознавателями и атрибутами слоя трассы роутера, 231 860
байт JSON; кодирование её в JSON стоит 2,7 мс:

| Уровень | Сжатая партия | Доля | macOS, zlib 1.2.12 | Linux, zlib 1.2.11 |
|---|---|---|---|---|
| 1 | 27 948 байт | 12,1 % | 0,30 мс | 0,36 мс |
| 2 | 26 980 байт | 11,6 % | 0,29 мс | 0,36 мс |
| **3** | **26 358 байт** | **11,4 %** | **0,30 мс** | **0,36 мс** |
| 4 | 24 159 байт | 10,4 % | 0,63 мс | 0,71 мс |
| 6 | 22 937 байт | 9,9 % | 0,81 мс | 0,88 мс |

(размеры — по macOS, у Linux они расходятся на десятки байт.) Уровни
с первого по третий — быстрый путь zlib, и стоят они одинаково;
третий из них сжимает лучше всех. С четвёртого zlib ищет совпадения
лениво, и работа растёт вдвое ради полутора процентов. Партия
ужимается почти в девять раз. Больше не выжать: шестнадцатеричные
опознаватели случайны, сжимаются не больше чем вдвое, и на них
приходится около половины сжатой партии.

Узел без zlib узнаёт об этом отказом `start`, а не броском на каждом
такте, после которого партия пропала бы без счёта:

```lua
otlp.start({ service_name = 'panel' })
--> nil, клиент к коллектору не собран: сжимать gzip нечем — нет системной библиотеки zlib: …; без сжатия — compression = «none»
otlp.start({ service_name = 'panel', compression = 'none' })   --> true
```

Сжатие — настройка отправки, а не партии: ждущая партия после
перенастройки уходит так, как велит новая. Повтор той же партии уходит
тем же до байта: и кодировщик, и zlib на одном входе дают один выход.

Проверено на стенде (`make otel-up`, коллектор `grafana/otel-lgtm`):
партия gzip принята, и её отрезок найден в Tempo; полная партия
в 512 отрезков ушла сжатой больше чем впятеро и дошла до Tempo;
несжатая партия тоже принимается. Коллектор разжимает тело по заголовку
и только по нему: заголовок gzip при несжатом теле — 400
«gzip: invalid header», сжатое тело без заголовка не принимается.

## Что уходит коллектору

Тело — `ExportTraceServiceRequest` в ProtoJSON, и три правила в нём
коллектор проверяет строго — это проверено на настоящем коллекторе
(раздел «Проверки»):

- `traceId` и `spanId` — **шестнадцатеричной строкой**, а не base64:
  на base64 коллектор отвечает 400 «length mismatch»;
- `startTimeUnixNano` и `endTimeUnixNano` — **десятичной строкой**:
  int64 в double теряет наносекунды выше 2⁵³;
- `kind` и `status.code` — целыми по перечислениям OTLP: `internal` 1,
  `server` 2, `client` 3, `producer` 4, `consumer` 5, прочее — 0;
  статус пишется только у отрезка с ошибкой (`code = 2`, `message` —
  текст отказа).

Отрезок несёт `parentSpanId` и `traceState`, если они есть, `flags` —
восемь бит `trace_flags` заголовка, атрибуты списком `{ key, value }`
по алфавиту ключей. Число-атрибут — `intValue` строкой, если оно целое
и умещается в int64, иначе `doubleValue`; NaN и бесконечности уходят
строкой: `json` пишет их литералами, которые не JSON, и коллектор отверг
бы всю партию.

**Тайны вырезаются правилом `tnt-log`** перед отправкой: атрибут с именем
тайны (`authorization`, `db.password`, …) уходит как `[скрыто]`, строки —
имя отрезка, текст ошибки, строковые атрибуты — проходят `log.scrub`.
Класть тайны в атрибуты не надо и так, но граница процесса — последнее
место, где их можно остановить.

Один ресурс, одна область, отрезки партии по порядку закрытия:

```lua
otlp.encode.request({ {
    trace_id = '4bf92f3577b34da6a3ce929d0e0e4736', span_id = '00f067aa0ba902b7',
    name = 'GET /customers/:id', kind = 'server', trace_flags = '03',
    started = 1700000000000000000LL, finished = 1700000000250000000LL,
    status = 'unset', attributes = {},
} }, { ['service.name'] = 'panel' })
```

```json
{"resourceSpans":[{"resource":{"attributes":[{"key":"service.name","value":{"stringValue":"panel"}}]},
  "scopeSpans":[{"scope":{"name":"tnt-trace"},"spans":[{"traceId":"4bf92f3577b34da6a3ce929d0e0e4736",
    "spanId":"00f067aa0ba902b7","name":"GET /customers/:id","kind":2,
    "startTimeUnixNano":"1700000000000000000","endTimeUnixNano":"1700000000250000000","flags":3}]}]}]}
```

## Чем пришлось поступиться

- **Выгрузка не ровно однократна**: партия, принятая коллектором, чей
  ответ потерялся, уйдёт второй раз. Если повтор пришёл, пока трасса
  живая, Tempo показывает её отрезки дважды, а метрики отрезков считают
  копию всегда (раздел «Повтор после потерянного ответа»).
- **При перегрузе теряются новые отрезки**, а не старые: очередь
  `tnt-trace` отбрасывает сверх потолка, и трасса с отброшенными
  отрезками приходит дырявой — это видно по `dropped`.
- **Всплеск без уступки будильник не спасает**: такт идёт, только когда
  файбер, закрывающий отрезки, уступит управление, и больше потолка
  очереди (2048) отрезков подряд без единой уступки теряют лишнее.
- **Остановка не досылает**: `stop()` не ждёт коллектора, и очередь
  остаётся в `tnt-trace`, ждущая партия — в модуле до следующего `start`.
  Кому нужно дослать, зовёт `flush()` до `stop()`.
- **Повтор с опозданием до такта**: срок повтора сверяется на такте,
  а не будит цикл.
- **Сервер, просящий ждать дольше 30 с, теряет партии**: выгрузчик
  не держит очередь дольше потолка, а следующая партия уходит в свой
  такт и может получить тот же ответ.
- **Сжатие стоит узлу**: 0,3–0,4 мс на полную партию в потоке событий,
  сверх 2,7 мс её кодирования в JSON. Пула нитей под сжатие у Tarantool
  нет; между кусками по 64 КБ `tnt-compress` уступает управление.
- **Сжатие только gzip**: OTLP называет только его, а библиотек zstd
  и прочих в поставке узла нет — zlib есть всегда.
- **Журналы по OTLP не выгружаются**: встроенный журнал пишет `trace_id`
  верхним полем, и сборщик журналов связывает записи с трассой сам.
- **Ждущая партия одна**: пока коллектор не принял её, новых партий цикл
  не берёт — порядок отрезков в трассе дороже скорости.
- **Отрезки уходят в один приёмник**: очередь `tnt-trace` одна, и пока
  её снимает Sentry, выгрузчик не запускается, а при идущем выгрузчике
  Sentry не запускается с отрезками (раздел «Очередь снимает кто-то
  один»). Трассы в коллектор и отрезки в Sentry разом не уходят.
- **Настройки, клиент, ждущая партия и счётчики — на модуль**: загруженный
  второй раз модуль (в проверках — заново на каждую проверку) считает
  с нуля.

## Проверки

Кодировщик — эталонными таблицами и телом, разобранным обратно из JSON.
Приговор — таблицей векторов по кодам. Сжатие — настоящей zlib через
`tnt-compress`: тело партии сверяется байт в байт с ней же на третьем
уровне и отличается от соседних; узел без zlib — внешней зависимостью
загрузчика `tnt-compress` (`compress._set_source({ load = … })`).
Выгрузчик — на настоящих трассе, контексте, клиенте и цикле,
загруженных заново на каждую проверку, с двойником libcurl: по нему
видно, что и с какими заголовками ушло коллектору, — партия внутри
трассы не рождает отрезка и не несёт `traceparent`. Одновременные
отправки проверяются слоем клиента (`client.layers`), который держит
отправку в пути. Будильник — всплеском 5000 отрезков за 0,1 с при такте
в час: с ним не отброшено ни одного и ушло не меньше десяти партий,
а отрицательный контроль — тот же всплеск со снятым будильником — теряет
всё сверх потолка очереди. Часы, имя узла и признак Sentry, снимающего
очередь, подменяются как внешние зависимости
`otlp._set_source({ monotonic, instance, rival, module })`, а сам Sentry
и очереди договора — двойниками модулей в `package.loaded`: зависимости
от них у пакета нет и в проверках. Крюк, поставленный загруженным
очередям процесса, проверки снимают сами: список крюков очереди живёт
дольше проверки.

Проверки лежат в `test/` и идут на luatest. Покрытие строк — 100 %,
убитых мутантов — 100 %.

### Живые проверки

```sh
make otel-up                  # grafana/otel-lgtm: OTLP/HTTP 14318, Tempo 13200, Grafana 13000
make otel-down
```

`otlp_live_test.lua` против настоящего коллектора: партия принята (200),
отрезок найден в Tempo по опознавателю — именно отрезок, а не трасса:
трассу из одних нулей коллектор принимает с 200, но найти её нечем;
так — и сжатая gzip партия, и несжатая, а полная партия в 512 отрезков
уходит сжатой больше чем впятеро и тоже доходит до Tempo;
клиентский отрезок попытки `tnt-http` приходит с серверным родителем;
одна и та же партия уходит дважды, потому что слой клиента
(`client.layers`) теряет первый ответ коллектора. Если повтор пришёл
в живую трассу, Tempo показывает отрезок дважды, если в закрытую — один
раз, а метрики отрезков считают обе копии. Отрицательные контроли —
партия с base64 в опознавателях получает 400, заголовок gzip при
несжатом теле — тоже 400, а сжатое тело без заголовка не принимается.
Проверки повтора идут дольше прочих, до полуминуты: они ждут, пока
Tempo закроет трассу и посчитает метрики. Без стенда проверки
пропускаются: гейты не должны зависеть от докера. Трассы стенда видны
глазами в Grafana: `http://127.0.0.1:13000/`, служба
`tnt-trace-otlp-live`.
